---
title: Persistent Memory
description: Hierarchical, temporal memory for LLM applications. Enable your AI to remember across conversations with intelligent scoping and versioning.
---

LLMs have two fundamental limitations: context windows overflow with too much history, and every conversation starts from zero. Persistent Memory solves both by extracting key facts, persisting them, and injecting them when relevant.

This is **temporal compression** -- instead of carrying 10,000 tokens of conversation history, carry 100 tokens of extracted memories.

## Quick Start

```python
from openai import OpenAI
from headroom import with_memory

# One line -- that's it
client = with_memory(OpenAI(), user_id="alice")

# Use exactly like normal
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "I prefer Python for backend work"}]
)
# Memory extracted INLINE -- zero extra latency

# Later, in a new conversation...
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What language should I use?"}]
)
# Response uses the Python preference from memory
```

## How It Works

The `with_memory()` wrapper intercepts every chat completion call:

1. **Inject** -- Semantic search finds relevant memories and prepends them to the user message
2. **Instruct** -- Adds a memory extraction instruction to the system prompt
3. **Call** -- Forwards the request to the LLM
4. **Parse** -- Extracts the `<memory>` block from the response
5. **Store** -- Saves with embeddings, vector index, and full-text search index
6. **Return** -- Cleans the response (strips the memory block before returning)

Memory extraction happens **inline** as part of the LLM response. No extra API calls, no extra latency.

## Hierarchical Scoping

Memories exist at four scope levels, from broadest to narrowest:

| Scope | Persists Across | Use Case |
|-------|-----------------|----------|
| **User** | All sessions, all time | Long-term preferences, identity |
| **Session** | Current session only | Current task context |
| **Agent** | Current agent in session | Agent-specific context |
| **Turn** | Single turn only | Ephemeral working memory |

```python
from openai import OpenAI
from headroom import with_memory

# Session 1: Morning
client1 = with_memory(
    OpenAI(),
    user_id="bob",
    session_id="morning-session",
)
response = client1.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "I prefer Go for performance-critical code"}]
)
# Memory stored at USER level (persists across sessions)

# Session 2: Afternoon (different session, same user)
client2 = with_memory(
    OpenAI(),
    user_id="bob",
    session_id="afternoon-session",
)
response = client2.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What language for my new microservice?"}]
)
# Recalls Go preference from morning session
```

## Memory Categories

There is no dedicated `category` field on `Memory` or parameter on `add()`
(`headroom/memory/models.py`, `headroom/memory/core.py`) -- store a
free-form category string in the `metadata` dict instead, e.g.
`metadata={"category": "fact"}`. These are the conventional category values
used in Headroom's own examples for organization and retrieval:

| Category | Description | Examples |
|----------|-------------|----------|
| `"preference"` | Likes, dislikes, preferred approaches | "Prefers Python", "Likes dark mode" |
| `"fact"` | Identity, role, constraints | "Works at fintech startup", "Senior engineer" |
| `"context"` | Current goals, ongoing tasks | "Migrating to microservices", "Working on auth" |
| `"entity"` | Information about entities | "Project Apollo uses React", "Team lead is Sarah" |
| `"decision"` | Decisions made | "Chose PostgreSQL over MySQL" |
| `"insight"` | Derived insights | "User tends to prefer typed languages" |

## Memory API

The `with_memory()` wrapper exposes a `.memory` attribute for direct access:

```python
client = with_memory(OpenAI(), user_id="alice")

# Search memories (semantic)
results = client.memory.search("python preferences", top_k=5)
for memory in results:
    print(f"{memory.content}")

# Add a memory manually
client.memory.add(
    "User is a senior engineer",
    importance=0.9,
)

# Get all memories for this user
all_memories = client.memory.get_all()

# Clear all memories
client.memory.clear()

# Get stats
# `stats()` currently returns only {"total": N} -- there is no
# per-category breakdown (`headroom/memory/wrapper.py:342-348`).
stats = client.memory.stats()
print(f"Total memories: {stats['total']}")
```

## Temporal Versioning

When facts change, Headroom creates a **supersession chain** that preserves history:

```python
from headroom.memory import HierarchicalMemory, MemoryFilter

memory = await HierarchicalMemory.create()

# Original fact
# `category` is a convention, not a keyword argument -- `add()` has no
# `category` param (`headroom/memory/core.py`); store it in `metadata`.
orig = await memory.add(
    content="User works at Google",
    user_id="alice",
    metadata={"category": "fact"},
)

# User changes jobs -- supersede the old memory
new = await memory.supersede(
    old_memory_id=orig.id,
    new_content="User now works at Anthropic",
)

# Query current state (excludes superseded by default)
current = await memory.query(MemoryFilter(
    user_id="alice",
    include_superseded=False,
))
# Returns only "User now works at Anthropic"

# Get the full chain
chain = await memory.get_history(new.id)
# [
#   Memory(content="User works at Google", is_current=False),
#   Memory(content="User now works at Anthropic", is_current=True),
# ]
```

This gives you an audit trail, the ability to debug why the LLM made certain decisions, and rollback if needed.

## Backends

### Embedder Backends

```python
from headroom.memory import MemoryConfig, EmbedderBackend

# ONNX embeddings (recommended -- fast, free, private; ~30 MB int8-quantized)
# Note: EmbedderBackend.LOCAL requires PyTorch (~2 GB); use ONNX instead.
config = MemoryConfig(
    embedder_backend=EmbedderBackend.ONNX,
    embedder_model="BAAI/bge-small-en-v1.5",
)

# OpenAI embeddings (higher quality, costs money)
config = MemoryConfig(
    embedder_backend=EmbedderBackend.OPENAI,
    openai_api_key="sk-...",
    embedder_model="text-embedding-3-small",
)

# Ollama embeddings (local server, many models)
config = MemoryConfig(
    embedder_backend=EmbedderBackend.OLLAMA,
    ollama_base_url="http://localhost:11434",
    embedder_model="nomic-embed-text",
)
```

### Embedding Runtime / GPU Offload (Apple Silicon)

By default the proxy's memory embedder runs on the **ONNX CPU** backend -- fast
and dependency-light, but CPU-only. Under sustained load the embedding step can
saturate the CPU and make the proxy less responsive.

On Apple Silicon you can opt in to running the embedder on the **Apple GPU
(MPS)** instead, which offloads that work off the CPU and keeps the proxy
responsive. Install the extra and set the env var:

```bash
pip install "headroom-ai[pytorch-mps]"   # also works as [pytorch_mps]
export HEADROOM_EMBEDDER_RUNTIME=pytorch_mps
```

When set, the embedder runs via the torch sentence-transformers backend on the
Apple GPU instead of the default ONNX CPU embedder. Notes:

- **Strictly opt-in.** `pytorch_mps` is the only accepted value; anything else
  (or unset) keeps the default ONNX CPU embedder. Default behavior is unchanged,
  and there is no CLI flag -- it is env-var only.
- **Auto-fallback.** It only activates when Apple MPS is actually available
  (Apple Silicon + torch). If MPS is unavailable or torch/sentence-transformers
  is not installed, it logs a warning and uses the existing default embedder
  selection path: ONNX when available, then the pre-existing local
  sentence-transformers fallback.
- **MPS serialization.** torch-MPS is not thread-safe, so the embedder
  serializes MPS encode calls internally via a single-worker executor. This is
  automatic -- there is nothing to configure.

### Storage

Storage uses **SQLite** for CRUD and filtering, **HNSW** for vector similarity search, and **FTS5** for full-text keyword search. All embedded -- no external services required.

```python
config = MemoryConfig(
    db_path="memory.db",
    vector_dimension=384,
    hnsw_ef_construction=200,
    hnsw_m=16,
    hnsw_ef_search=50,
    cache_enabled=True,
    cache_max_size=1000,
)
```

### Cognee Backend (Knowledge Graph)

The default storage above is fully embedded. As an alternative, Headroom can store memories in [cognee](https://github.com/topoteretes/cognee) -- an async AI-memory engine that builds a **knowledge graph** over your memories and supports both graph and vector retrieval.

Install the extra:

```bash
pip install "headroom-ai[cognee]"
```

Enable it on the `Memory` facade or the proxy:

```python
from headroom.memory import Memory

memory = Memory(backend="cognee")
await memory.save("User prefers Python for backend work", user_id="alice")
results = await memory.search("language preferences", user_id="alice")
```

```bash
headroom proxy --memory --memory-backend cognee
```

How it works:

1. **Save** -- each memory is added to a cognee dataset (default `headroom_memories`), tagged with `user:<id>`, `session:<id>`, and `entity:<name>` tags so retrieval can be scoped.
2. **Cognify** -- after each save, `cognee.cognify()` extracts entities and relationships and folds the memory into the knowledge graph. This step is LLM-bound and slow, so it runs **in the background by default** -- saves return immediately and never block the request path. Set `HEADROOM_COGNEE_AUTO_COGNIFY=false` to skip it and run cognify on your own schedule.
3. **Search** -- `cognee.search()` runs with the configured search type, scoped to the same tags. `CHUNKS` (the default) is raw retrieval with no LLM synthesis -- cheapest, and the right choice for a proxy request path. `GRAPH_COMPLETION` retrieves graph context instead (Headroom sends `only_context=True` so no LLM answer is generated).

Configuration (explicit argument or CLI flag > env var > default):

| Env Var | Proxy Flag | Description | Default |
|---------|------------|-------------|---------|
| `HEADROOM_COGNEE_DATASET` | `--memory-cognee-dataset` | cognee dataset that holds all Headroom memories | `headroom_memories` |
| `HEADROOM_COGNEE_SYSTEM_ROOT` | `--memory-cognee-system-root` | Directory for cognee system state (databases, caches). Keeps Headroom's cognee state isolated from other cognee installs. | cognee's default |
| `HEADROOM_COGNEE_DATA_ROOT` | `--memory-cognee-data-root` | Directory for cognee data storage | cognee's default |
| `HEADROOM_COGNEE_SEARCH_TYPE` | `--memory-cognee-search-type` | cognee `SearchType` name used for retrieval (e.g. `CHUNKS`, `GRAPH_COMPLETION`) | `CHUNKS` |
| `HEADROOM_COGNEE_AUTO_COGNIFY` | `--memory-cognee-auto-cognify` / `--no-memory-cognee-auto-cognify` | Run `cognee.cognify()` after each save so new memories join the knowledge graph | `true` |
| `HEADROOM_COGNEE_METADATA_DB` | `--memory-cognee-metadata-db` | Path to the SQLite file holding the backend's durable memory registry and delete/update tombstones. Proxy workers that must share memories (and see each other's deletions) must point at the same file. | `headroom_cognee_meta.db` under the data root, else the system root, else `~/.headroom` |

The same options are available programmatically via `CogneeConfig`:

```python
from headroom.memory.backends.cognee import CogneeBackend, CogneeConfig

backend = CogneeBackend(CogneeConfig(
    dataset_name="my_app_memories",
    search_type="GRAPH_COMPLETION",
    # background_cognify=True (default): cognify never blocks a save
))
```

**Requirements and limitations** (cognee v1.x):

- Headroom disables cognee's session memory (cognee >= 1.5 enables it by default) by setting `CACHING=false` if the variable is unset, as part of the one-time process-wide configuration: the session-aware layer adds an LLM call per search and can replay a previous turn's results, including content deleted through this backend. Export `CACHING` yourself to override.
- Searching a dataset that exists but was never cognified returns no results (cognee itself raises `NoDataError` there; the backend treats an empty store as an empty result).
- cognee needs an LLM provider for the cognify graph-build step. Configure it through cognee's own settings (e.g. `LLM_API_KEY`; cognee reads its environment and `.env` file). If the key is missing or cognify fails, the save itself still succeeds -- the enrichment failure is logged, never raised. Headroom snapshots the process environment around cognee's import (which happens once per process) and restores any pre-existing variables its `.env` load overwrote, so a `.env` in the proxy's working directory cannot silently override live environment variables.
- **cognee's configuration is process-wide and immutable.** `import cognee` and its root directories (`system_root` / `data_root`) are process-global, so the first backend initialized in a process fixes them for every later instance. Initializing another cognee backend in the same process with *different* roots raises `RuntimeError` (fail closed -- one tenant can never redirect another tenant's cognee storage); the same roots reuse the already-configured module. Run one cognee root configuration per process.
- cognee has **no per-item update API**. `update_memory` keeps the memory's ID: the durable registry row is rewritten in place (same ID, new content), the old content is tombstoned, and the new content is added to cognee as a fresh data item -- so searches keep returning the *original* ID for the updated content.
- **The deletion contract depends on the search type.** Under `CHUNKS` (the default), results are verbatim stored text and the durable tombstones are authoritative: `delete_memory` removes the registry row, tombstones the content, and additionally attempts a hard delete through cognee's dataset API (`cognee.datasets.list_data` / `delete_data`, matched by content hash) to reclaim storage. Tombstones match in both directions (a chunk that is a fragment of deleted content is filtered too), so nothing derived from tombstoned text can pass the read path -- the delete succeeds even when the hard delete cannot be proven. Under any **other** search type, results may be graph-synthesized text that no longer contains the deleted source, which tombstones cannot enforce; there, `delete_memory`/`update_memory` succeed only when the hard delete is **proven** (matched, deleted, verified gone) and otherwise raise `CogneeDeletionUnverifiedError` -- delete still tombstones the content and keeps the memory for retry, update refuses before changing anything. The backend never reports a deletion it cannot stand behind.
- The memory registry and tombstones live in a small **SQLite metadata store** (`HEADROOM_COGNEE_METADATA_DB`, WAL mode), so deletions and updates survive proxy restarts and apply immediately to every proxy worker sharing the same file.
- Memory IDs are stable, content-derived UUIDs resolved through the durable registry, so IDs returned by `memory_search` can be passed to `memory_update` / `memory_delete` -- across restarts and across workers sharing the metadata store (cognee has no fetch-by-id API for raw memories).
- Search scores are rank-based (descending with result order, mapped into the `(0.5, 1.0]` band) -- cognee does not expose similarity scores. Consequently `--memory-min-similarity` values of 0.5 or below (including the 0.3 default) have no filtering effect with this backend.
- `importance` is recorded in the returned memory's metadata; cognee does not rank by it.

## Provider Compatibility

Memory works with any OpenAI-compatible client:

```python
from openai import OpenAI
from headroom import with_memory

# OpenAI
client = with_memory(OpenAI(), user_id="alice")

# Azure OpenAI
client = with_memory(
    OpenAI(base_url="https://your-resource.openai.azure.com/..."),
    user_id="alice",
)

# Groq
from groq import Groq
client = with_memory(Groq(), user_id="alice")
```

## Performance

| Operation | Latency | Notes |
|-----------|---------|-------|
| Memory injection | &lt;50ms | Local embeddings + HNSW search |
| Memory extraction | +50-100 tokens | Part of LLM response (inline) |
| Memory storage | &lt;10ms | SQLite + HNSW + FTS5 indexing |
| Cache hit | &lt;1ms | LRU cache lookup |
