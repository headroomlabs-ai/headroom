# SDK contract compiler — experimental pilot

Read `docs/engineering/deterministic-sdk-generation.md` for the architecture and phased rollout, and `docs/engineering/sdk-generation-pr-405-review.md` for the motivating source review.

## Commands from a Headroom checkout after installation

```sh
python -m tools.sdkgen generate
python -m tools.sdkgen check
python -m unittest discover -s tests/sdkgen -p 'test_*.py' -v
python -m tools.sdkgen.conformance
python -m tools.sdkgen inventory --scan headroom > sdk-surface-inventory.json
python -m tools.sdkgen diff old-openapi.json sdk/generated-pilot/openapi.json
```

Use `--fixture` on generate/check/conformance only in the standalone delivered bundle. Source mode is the default and fails rather than silently using fixtures. The unit tests automatically prefer the actual `headroom/proxy/server.py` when present. Inventory is a candidate report, not a complete route-graph or public-API coverage certification.

The compiler uses only the Python standard library; Python 3.11+ is needed. The additive metadata module is compatible with Python 3.10 syntax. Conformance additionally needs Go, Node and TypeScript, Rust/Cargo, and the .NET SDK. See `toolchain.lock.json` for exact local and CI tool versions. No provider credentials, network downloads during generation, or proxy startup are needed to generate the committed snapshots. Native dependency downloads occur only when compiling the Rust client for the first time.

## Scope and ownership

The pilot generates exactly two operations: POST `/v1/retrieve` and GET `/v1/retrieve/{hash_key}`. Outputs are experimental and isolated under `sdk/generated-pilot`. No existing language SDK is replaced and no package is published.

Edit `headroom/proxy/sdk_contracts.py` and exported source metadata, not generated files. Edit runtime seeds in `tools/sdkgen/runtime`. `check` verifies all generated bytes and the input/output hashes. The generated `.ruff.toml` keeps formatters from rewriting compiler-owned Python output; handwritten compiler/runtime/test files remain lintable.

Supported model profile: direct TypedDict, required/optional, nullable, scalars, homogeneous Literal, list, map with string keys, explicit JsonValue. Unsupported types/operations fail. The current endpoint profile is JSON with 200 success, named request/response objects and string path parameters; no query/header serialization, auth scheme adapters, Pydantic/dataclass harvesting, multipart, async Python, SSE, or WebSockets yet.

The generated `RetrievalError` describes declared error JSON, but kernels expose HTTP errors uniformly with status, headers, and raw body. They do not automatically deserialize every declared error model. Do not mistake error schema coverage for language-specific exception taxonomy generation.

## Language extension contract

An emitter receives the compiled OpenAPI document (through `render` and its extracted model/operation maps) and returns deterministic relative paths and byte strings. Add a local emitter in `tools/sdkgen/emit.py`, register it in `render`, reject unsupported schemas before rendering, and qualify its runtime with the shared wire cases. Names must be collision-checked. Never emit `any` or an opaque blob to hide a type-adapter failure; opaque JsonValue is an explicit source decision.

The mature implementation can substitute qualified, pinned OpenAPI Generator backends at this boundary without changing ownership of the server schema. The current hand-authored runtime seeds are reference kernels, not a universal provider streaming implementation.

## Tests before a draft PR

Run repository-pinned Ruff and mypy checks, regenerate, and then run compiler and five-language conformance tests. The checked-in workflow performs all of these gates with pinned tools. If formatting changes generator or runtime source, regenerate before `check` because input hashes deliberately change.

After these isolated tests, run the project's supported full proxy and existing SDK suites. Validate middleware, same-origin/loopback enforcement, application startup, supported Python versions and the actual CI workflows before declaring the feature production-ready.
